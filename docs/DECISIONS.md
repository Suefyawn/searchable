# Architecture Decision Records

Format: **ADR-n · Title**, Status · Date. Context → Decision → Consequences.

---

## ADR-1 · One Next.js app, no separate backend
**Accepted · 2026-09-15**
Context: Solo founder; site + admin + API + jobs. Decision: single Next.js 16 App Router codebase; Server Components for reads, Server Actions for writes, route handlers for external calls. Consequences: one deploy, one type system, no API contract drift. Revisit only if a non-JS consumer needs a stable API (then expose `/api/v1`).

## ADR-2 · Postgres is the only database; Drizzle is the ORM
**Accepted · 2026-09-15**
Context: Need FTS, JSONB, generated columns, real migrations, and a path to Supabase. Decision: Drizzle with the `postgresql` dialect; schema in TypeScript; SQL migrations committed under `drizzle/`. Consequences: portable across any Postgres host; no vendor SDK in domain code.

## ADR-3 · PGlite for local development instead of Docker/Supabase-local
**Accepted · 2026-09-15**
Context: Docker is not installed on the dev machine; the founder wants to build fully locally before opening any accounts. Decision: `@electric-sql/pglite` (Postgres compiled to WASM) persisted at `.data/pglite`, selected via `DATABASE_URL=pglite://…`. Consequences: zero-install, real Postgres semantics, same Drizzle code as production. Limits: single connection, no PostGIS (use lat/lng + haversine until Supabase), no Supabase Auth locally (→ ADR-4). If Docker is installed later, `supabase start` is a drop-in alternative; nothing in the app changes.

## ADR-4 · better-auth instead of Supabase Auth
**Accepted · 2026-09-15**
Context: ADR-3 removes Supabase Auth locally; two auth systems would be worse than one. Decision: better-auth with the Drizzle adapter; email/password first, OAuth (Google) later; `users.role` for authorisation. Supabase is used as managed Postgres (+ Storage), not as an auth provider. Consequences: identical auth locally and in prod; portable. Trade-off: no Supabase RLS-based row security, authorisation lives in server code (`requireRole`), which is where it belongs for an RSC app that never exposes the DB to the browser.

## ADR-5 · Search is a single write-through index table
**Accepted · 2026-09-15**
Context: Federated search across 6+ entity types must exist on Day 1. Decision: `search_documents(entity_type, entity_id, url, title, summary, body, city, category, tsv, boost, published_at)` with a generated `tsvector`; every mutation upserts its document; ranking in SQL. Consequences: one query, one ranking function, trivially re-indexable; swappable for Typesense/Meili by re-implementing `src/lib/search.ts` only.

## ADR-6 · Tools are code, configured by versioned data
**Accepted · 2026-09-15**
Context: 300 calculators cannot be hand-built pages; tax tables change yearly. Decision: `ToolDefinition` interface; generic renderer; rate tables in `src/tools/data/*` with `effectiveFrom` + `source`; tool metadata mirrored into `tools` table for search/SEO. Consequences: a new tool is one file; a FY change is a data edit + review date bump.

## ADR-7 · Articles: one table, `kind` column
**Accepted · 2026-09-15**
Context: news, guides, explainers share 90% of fields and the same workflow. Decision: single `articles` table with `kind` enum and `categories.kind` scoping. Consequences: one editor, one search doc type with sub-type boost, simple cross-linking.

## ADR-8 · Locations are a self-referential tree
**Accepted · 2026-09-15**
Decision: `locations(id, parent_id, kind: country|province|city|area, slug, name, lat, lng)`. City × category pages resolve `city` from this table. Consequences: areas, districts, tehsils fit without schema changes.

## ADR-9 · Entities as first-class knowledge graph nodes
**Accepted · 2026-09-15**
Decision: `entities` + polymorphic `entity_links(entity_id, target_type, target_id, relation)`. Consequences: entity hubs and later AI grounding come for free from linking discipline in the editor.

## ADR-10 · No dates in URLs; `/b/[slug]` for businesses
**Accepted · 2026-09-15**, see `docs/URL-ARCHITECTURE.md`.

## ADR-11 · npm, not pnpm/yarn
**Accepted · 2026-09-15**, already installed; nothing else to set up. Revisit if the repo becomes a monorepo.

## ADR-12 · Design system is hand-rolled primitives, shadcn-compatible
**Accepted · 2026-09-15**
Context: The user asked for a clean, modern, highly readable UI. Decision: Tailwind v4 tokens in `globals.css`; small set of primitives in `src/components/ui` following shadcn conventions (`cn()`, variants) so shadcn components can be dropped in later without restyling. Consequences: no CLI dependency in the scaffold; full control of typography and spacing.

## ADR-13 · `marked` for Markdown, `@tailwindcss/typography` for prose
**Accepted · 2026-09-15**
Context: Articles and guides are authored in Markdown by trusted editors; the site needs excellent reading typography. Decision: `marked` (small, fast, GFM) renders on the server; `@tailwindcss/typography` `prose` classes style the output with our tokens. Consequences: no client-side Markdown; editor content is trusted (admin-only), if user-generated Markdown is ever rendered, add sanitisation (`DOMPurify`/`rehype-sanitize`) first.

## ADR-14 · Visual redesign: display typeface, soft surfaces, glass header
**Accepted · 2026-09-15**
Context: The founder judged the first pass "old fashioned". Decision: Bricolage Grotesque (display, variable opsz/wdth) for headings + Inter for body; warm off-white canvas with radial gradient glows on the hero; borderless cards with layered shadows and hover lift; pill buttons and chips; floating glass header; dark editorial footer; per-category colour accents for tools; live data ticker on the home page. Tokens live in `globals.css` (`surface`, `surface-hover`, `glass`, `eyebrow`, `text-gradient`, `hero-bg`). Consequences: every page inherits the language through primitives; dark mode is preserved via the same tokens; motion respects `prefers-reduced-motion`.

## ADR-15 · Minimal news design (supersedes ADR-14)
**Accepted · 2026-09-15**
Context: The founder wants Searchable to look like a news website, minimalistic and easy on the eyes, and rejected rounded buttons/fields and glossy effects as old-fashioned. Decision: Newsreader (serif) for headlines and deks; Inter for article body, UI and meta (founder preference: body must be sans). Square corners everywhere (all radius tokens are 0). Hairlines instead of cards and shadows; a heavier rule above section titles; small-caps sans labels; one quiet green accent for labels and links; near-black primary buttons; a classic masthead (date line, wordmark, section nav, small search) and a light footer. The home page is a front page: search bar, numbers strip, lead story + secondary column + latest headlines, calculators, guides, directory. Consequences: no gradients, glass, pills or entrance animations anywhere; new components should use `hairline`, `rule`, `eyebrow`, `headline-link`, `surface` (white + 1px border) from `globals.css`.

## ADR-16 · Image uploads: sharp → WebP, local disk now, Supabase Storage later
**Accepted · 2026-09-15**
Decision: `POST /api/upload` accepts JPEG/PNG/WebP/GIF/AVIF ≤ 8 MB, normalises with `sharp` (rotate, resize per variant: article 1800px, cover 2000px, photo 1600px, logo 512px; WebP q82; metadata stripped), records a `media` row, and stores via `putObject()`, `STORAGE_PROVIDER=local` writes `public/uploads/YYYY/MM/<uuid>.webp`; `supabase` uploads to the `media` bucket over the Storage REST API. Editors may upload anything; business owners only for businesses they manage. Consequences: one adapter to switch at go-live; images served through `next/image` with `remotePatterns` already open for the Supabase host.

## ADR-17 · Openly licensed photography via Openverse; never AI-generated imagery
**Accepted · 2026-09-15**
Context: The founder wants real, relevant photos and no AI-generated images anywhere. Decision: photos come from the Openverse API (Flickr, Wikimedia Commons, museums) restricted to CC0 / public domain / CC BY / CC BY-SA; every import stores creator, licence and source page in `media` and renders a credit line under the image. Editors pick photos in the article editor; `scripts/seed-images.ts` seeds articles, cities and categories. Consequences: attribution is a first-class field (`featuredImageCredit`, `imageCredit`); the Wikimedia API is unreachable from some networks but the image hosts are, so Openverse is the single search path; anonymous limit 200/day, register a client id at go-live.

## ADR-18 · Monetization: manual invoices first, gateway later; placement is sold, editorial never is
**Accepted · 2026-09-15**
Decision: `orders` (business plans, sponsored posts, placements) and `submissions` (guest / sponsored / press release) tables; prices in `src/content/pricing.ts`; invoices `SP-YYYY-NNNNNN` with bank / JazzCash / Easypaisa details; admin marks paid, which sets tier, expiry and verification; cron lapses plans. Sponsored articles carry a disclosure block, a Sponsored badge and `rel="sponsored"` on outbound links; free listings link `nofollow`, paid tiers follow. AdSense loads only when `NEXT_PUBLIC_ADSENSE_CLIENT` is set and never inside tools or search. Consequences: a card gateway (Safepay/PayFast) is another `provider` value on the same order; see `docs/MONETIZATION.md`.

## ADR-19 · Directory growth: CSV import, dedupe by phone/name/geo, area pages, click-to-load OSM map
**Accepted · 2026-09-15**
Decision: `src/lib/import.ts` parses CSV, validates rows, normalises phones to +92, resolves category/city/area by slug or name (with aliases), runs `findDuplicates()` (same phone → same name key in city → Dice ≥ 0.8 within 300 m / ≥ 0.9 in city) and previews before committing to the review queue. Admin can merge a duplicate (status `duplicate`, reviews/leads moved, 301 redirect). Area pages `/businesses/[category]/[city]/[area]` and `/cities/[city]/[area]` are `noindex` under 5 listings. Maps are a click-to-load OpenStreetMap iframe on profiles, no map library until local search needs multi-pin maps (MapLibre then). Consequences: `pg_trgm` is not required; dedupe runs in JS over the city's rows, which is fine to ~20k listings per city.

## ADR-20 · Light theme only; hero-first home page without a search box
**Accepted · 2026-09-15**
Context: The founder wants black-on-white, minimal and modern, and judged the search-box-first home "not suitable" and lacking a hero. Decision: the site ships light only, `--bg: #ffffff`, near-black type; the dark palette stays in `globals.css` but applies only under an explicit `data-theme="dark"` (Tailwind `dark:` is remapped to that attribute, the OS preference is ignored). Home: a thin scrolling numbers ticker, then a hero of the lead story (photo 7/12, headline stack 5/12 with three text headlines), then a four-up photo grid, calculators with example results, guides with thumbnails, directory, cities, newsletter. ## ADR-21 · Automated data ingestion from public sources with jump guards
**Accepted · 2026-09-15**
Decision: `src/lib/ingest.ts` pulls the data hub's core series daily (`/api/cron/ingest`, also "Fetch now" in `/admin/data`): SBP's economic-data page (USD/PKR M2M, 12-month KIBOR offer, policy rate), open.er-api.com cross rates for AED/SAR/GBP/EUR anchored on SBP's USD/PKR, PSO's fuel-price page (Premier Euro 5, Hi-Cetane diesel), and spot gold/silver from gold-api.com converted to per-tola PKR. A reading that moves more than 30% from the last stored value is held ("rejected") rather than published, so a parser break cannot poison the site; an editor can force it. Every auto reading carries a note naming the source and "(auto)". OGRA notifications remain the legal source for fuel prices and are PDFs; PSO's ex-depot price is what consumers pay and is parsed instead. CPI and solar per-watt stay manual. Consequences: seed values are illustrative placeholders replaced on first run; sources are third-party HTML and will need parser upkeep, failures surface in the admin panel, not silently.

## ADR-24 · Built for free tiers: CDN-first, R2 images, opportunistic scheduler, email budget
**Accepted · 2026-09-15**
Context: The founder's rule is that going live on Supabase, Vercel, Resend and friends must not run out of free usage; images should sit on Cloudflare. Decision (details in `docs/FREE-TIER.md`): every public page is static or ISR and every API that browsers poll carries `s-maxage`; search suggestions are matched in the browser from one cached JSON file; anonymous visitors never trigger a session request (a readable `sp_auth` hint cookie gates it) and signed-in sessions use better-auth's cookie cache; images are written once with 480/960 px renditions to Cloudflare R2 through a hand-signed S3 PUT (no SDK) and served as plain `<img srcset>` with `images.unoptimized`; crons are daily only, with `runDueJobs()` doing the five-minute work from requests that already happen (guarded by a `settings` row) and an external free pinger recommended; `sendEmail()` enforces daily and monthly counters with a transactional reserve and newsletter sends resume across days; daily pruning keeps analytics and search logs bounded; serverless functions hold one pooled connection. Open question deferred to go-live: Vercel Hobby forbids commercial use, so the host is either Vercel Pro once ads pay for it or Cloudflare Workers via OpenNext (free, commercial allowed); nothing in the code is Vercel-specific except `vercel.json`. Consequences: no `next/image`, no Supabase Storage in production, no 5-minute cron; a new dependency is not needed for R2.

## ADR-25 · Ownership claims with proof tied to the listing, and claim outreach
**Accepted · 2026-09-15**
Context: The directory is pre-listed from public sources; the plan is to email every listed business and ask it to claim, then sell the Verified badge from the dashboard. A claim has to be fool-proof without a paid SMS gateway. Decision (`src/lib/claims.ts`): four proofs, each bound to something already on the listing. (1) Invite link: a signed, 60-day, address-bound token emailed to the listing's address; using it proves control of that mailbox and approves on the spot. (2) Website-domain code: a six-digit code emailed to any mailbox on the listing's website domain (shared providers like gmail are refused), five attempts, 24 hours, auto-approved. (3) Phone: the claimant sends "CLAIM <code>" from the listed number to our WhatsApp/SMS number, or asks for a call; an editor confirms. (4) Document: NTN, registration, utility bill, letterhead or signboard photo, editor-reviewed. Every claim records role, contact and a declaration; one pending claim per user per listing; pending claims expire after 30 days; approval sets the owner, stamps `claimedAt`, rejects competing claims and emails next steps including the Verified badge. Unclaimed profiles say so and invite the claim. Outreach (`/admin/outreach`): a daily drip within the email budget, best-known listings first, one reminder after 14 days, one-click opt-out, plus a per-listing invite link in admin for manual sends. Consequences: migration 0006; `CLAIM_WHATSAPP_NUMBER`; on the free email plan outreach runs at roughly 80 a day.

## ADR-26 · Professional profiles: people, not shops
**Accepted · 2026-09-15**
Context: The founder wants doctors, electricians, engineers, architects and other professionals to have proper profiles: reachable, with handles, experience and a CV. Decision: a separate `professionals` table (not a business with a person's name) with a static profession list in `src/content/professions.ts` (36 professions in 11 groups, each with its licence body: PMDC, PEC, PCATP, Bar Council, ICAP, PNC). A profile carries headline, bio, city and area, workplace and service mode, phone, WhatsApp, optional public email, website, eight social handles, languages, skills, services with fees, experience, education, certifications, registration number, availability, a rate, a photo and a PDF CV (public or private). URLs: `/professionals` hub, `/professionals/[profession]`, `/professionals/[profession]/[city]` (noindex under three profiles), `/p/[slug]`. Profiles are created by the account that owns them (two per account), reviewed by an editor before going live, indexed in search as `professional` with a `person` intent that outranks businesses for "doctor in lahore" type queries, and rendered as Person JSON-LD with credentials and sameAs handles. Verified is a paid annual plan (Rs 4,900, `professional_plan` orders) or an editor's manual mark after checking the register and an identity document; the badge drops if name or profession changes on a free profile. Enquiries go to a per-profile lead table and the owner dashboard. Consequences: migration 0007 (new enum values on `search_entity_type` and `order_kind`, `orders.professional_id`); CV uploads add PDF support to storage; reviews for professionals reuse nothing yet and are a later addition.

## ADR-27 · Community: member posts with approval, comments and likes everywhere, moderation
**Accepted · 2026-09-15**
Context: The founder wants members to post jobs, listings, auctions and anything else (approved by an editor), with comments, replies and likes on posts and on our own content, member profiles, and a way to moderate. Decision (`src/db/schema/community.ts`, migration 0008): `member_profiles` (one per account: handle, display name, bio, photo, handles, verified and banned flags, counters, public page `/u/[handle]`), `posts` (five kinds with kind-specific JSON meta: job, listing, auction, question, discussion; statuses pending, published, rejected, hidden, closed; images; pinned; verified mark inherited from a verified member, business or professional), `bids` (auctions: minimum increment, end time, highest bid kept on the post), `comments` (one level of replies, on posts and articles; links from members hold for review, everything else goes up at once) and `reactions` (one like per user per target on posts, comments and articles). Posts by members wait for an editor; editors' own posts publish at once. Jobs close after 45 days, listings after 30, auctions at their end time (daily job). Anonymous readers never trigger a session request: forms and like state are gated on the sign-in hint cookie, which now carries the user id so "delete your own comment" needs no lookup, and one `/api/community/liked` call per page fills like state for signed-in readers. Search indexes published posts as `post` with a `market` intent for job and for-sale queries; job posts render JobPosting JSON-LD, listings and auctions Product, the rest DiscussionForumPosting. Moderation lives at `/admin/community` (approve, reject with a note, hide, pin, verify; comments; reports on posts, comments and members; verify or ban members, which hides their live content). Consequences: reports gained post, comment, professional and member targets; article pages gained a like and a comments section; rate limits per user on posts, comments and bids.

## ADR-28 · Shared inbox in admin on Resend receiving
**Accepted · 2026-09-15**
Context: The domain's MX points at Resend and receiving is verified, so mail to any @searchable.pk address lands there; the founder wants those mailboxes readable and answerable from admin rather than in a separate client. Decision (`src/lib/inbox.ts`, migration 0011): each received message is mirrored into `inbox_messages` keyed by Resend's id (sender, recipients, subject, snippet, plain text capped at 20k characters, attachment metadata, message-id) so admin has read and status state and a copy that outlives the provider's retention; HTML bodies and attachments are never stored and are fetched live when opened (HTML in a fully sandboxed iframe, attachments via a short-lived signed URL behind an editor-only redirect route). Two ways in: the signed `email.received` webhook at `/api/webhooks/resend` (Svix-style HMAC checked by hand, no dependency) and `syncInbox()` in the five-minute job runner as the safety net (one list call plus one detail call per unseen message, capped at 25). Messages are grouped by mailbox (the local part of our address) with new, replied, archived filters and a search. A reply goes out from the same mailbox through `sendEmail()` with In-Reply-To and References so it threads at the other end, quotes the original, counts against the transactional email budget, and marks the message replied. Consequences: `sendEmail()` accepts `from`, `replyTo` and `headers`; the Resend key must be full access for the receiving endpoints; `RESEND_WEBHOOK_SECRET` is optional (without it the endpoint refuses everything and the sync does the work); the contact form's `messages` queue stays separate because it is not email.

## ADR-29 · Admin API for automation, reusing the dashboard's actions
**Accepted · 2026-09-15**
Context: The founder wants a scheduled Claude task to run the site day to day: publish and update stories six times a day, record data, moderate queues, answer mail, assemble the newsletter. That needs a machine interface with exactly the safeguards a human editor gets. Decision: `Authorization: Bearer $ADMIN_API_KEY` is honoured inside `getSessionUser()` (constant-time compare, key at least 32 characters, never a browser session) and resolves to the first admin account, so every existing server action and `requireRole()` guard works unchanged from a route handler; the API is therefore a thin layer of JSON routes under `/api/admin/*` (`src/lib/admin-api.ts` wraps auth, JSON parsing, Zod errors and an `admin_api` analytics event per write) that speak in slugs (categories, cities, series, entities from `GET /reference`) and call `saveArticle`, `commitImport`, the moderation actions, `addDataPoint`, `runIngestion`, the inbox and newsletter libraries. Articles can take a photo as an Openverse query (credit recorded) or an openly licensed URL (`src/lib/media-import.ts`); nothing else. `GET /context` gives the automation the state it needs to avoid repeating itself. The playbook and the exact prompt for the scheduled task live in `docs/DAILY-TASK.md`. Consequences: no second auth system, no duplicated validation; the key is as powerful as the admin login and is rotated by changing one env var; every route is documented in `docs/ADMIN-API.md`.

## ADR-32 · The charcoal and blue kit, tunable from admin

## ADR-35 · Living price lists
**Accepted · 2026-09-17**
Context: Semrush (pk) shows "<model> price in pakistan" is the largest cluster of low-competition searches in the country (dozens of phone models at 40k to 200k searches a month, KD 12 to 29; Honda 125 and CD 70 at 110k and 90k), held today by thin pages. Decision: one engine for mobiles, bikes and cars: items in settings rows `prices:<category>` (zod in `src/lib/prices-shared.ts`), maintained by the scheduled task through `POST /api/admin/prices` from the makers' official Pakistan lists, with server-kept price history; pages `/prices`, `/prices/[category]`, `/prices/[category]/[slug]` (brand or model, resolved at request time), Product JSON-LD, PTA tax computed for phones from the FBR slabs and the live dollar rate. Consequences: the task fills 20 to 40 models a run; categories stay noindex until ten models; no new dependency.

## ADR-36 · Compete where we can win
**Accepted · 2026-09-17**
Context: The founder wants the most readers, but a young site cannot outrank Dawn, Geo or ESPNcricinfo on the day's headline. Decision: the task checks Semrush KD and the SERP before writing a hot story (KD over 55 and national outlets on top means our angle or skip), and spends most of every run on gaps (KD under 35, real volume, weak answers), which is what the backlog holds. ## ADR-38 · Agent surface: OpenAPI, API catalog, MCP, skill, WebMCP
**Accepted · 2026-09-17**
Context: Being cited by assistants is the site's primary goal; Cloudflare's agent-readiness scan listed the discovery documents agents look for. Decision: one read-only, key-free surface in `src/lib/agent-api.ts` (search, data series, calculator schema and run, page markdown) exposed three ways: REST (`GET/POST /api/tools/{slug}`, existing data, search and md routes, described by `/openapi.json` and catalogued at `/.well-known/api-catalog`, with `Link` headers on the home page); a minimal MCP server at `/mcp` (Streamable HTTP, JSON-RPC, tools only, no dependency) with its card at `/.well-known/mcp/server-card.json`; and a SKILL.md published through `/.well-known/agent-skills/index.json`. A tiny inline script registers the same three actions with WebMCP in browsers that have `navigator.modelContext`. Not adopted, on purpose: OAuth/OIDC discovery, protected-resource metadata and auth.md (nothing here needs an agent to authenticate), A2A card and DNS-AID (no agent endpoint to advertise), Web Bot Auth (the site sends no bot traffic), and every commerce protocol (ACP, AP2, MPP, UCP, x402: nothing is sold to agents). Consequences: `/mcp` and `/api/tools/*` share the search rate limit; every answer carries the canonical url to cite.

## ADR-39 · Audit hardening: escape, sign, header, and keep the rate limiter in memory
**Accepted · 2026-09-17**
Context: A full audit two days after go-live found one critical path (any signed-in member could get script into an editor's browser through post bodies and profile bios rendered by the editor-grade Markdown renderer, and through owner-editable taglines in search snippets), several public RPCs (helpers exported from `"use server"` files), sequential invoice URLs that showed payer details to anyone, no security headers, and every tool page shipping all 31 calculators to the browser. Decision: (1) two renderers in `src/lib/markdown.ts`: `renderMarkdown` for editor content keeps raw HTML, `renderUserMarkdown` for member content shows it as text; both refuse every href scheme except http(s), mailto and tel and escape attributes, so no sanitiser dependency is added. Search escapes text before `ts_headline`. A member's edit to a live post returns it to the queue. (2) Only actions are exported from `"use server"` files; `ensureMemberProfile`, `canEditBusiness`, `canEditProfessional` and `publishDueArticles` moved to plain modules. (3) Invoice links carry an HMAC of the invoice number (`orderPath()`); the page and the payment-reference action accept that key, the buying account or an admin, and answer 404 otherwise. (4) `next.config.ts` sets nosniff, Referrer-Policy, Permissions-Policy and a CSP of `frame-ancestors 'none'; object-src 'none'; base-uri 'self'`, relaxed to `frame-ancestors *` on calculator pages for `?embed=1`; a script CSP is not workable with AdSense and is not attempted. (5) Cron routes compare the secret in constant time and are closed in production without one; the seed refuses its default admin password off local PGlite. (6) The tool runner loads one calculator with a dynamic import (`src/tools/load.ts`) and paints the server-computed result first. Not adopted: a shared-store rate limiter (Upstash) needs a dependency and an account; the in-memory limiter plus the five-attempt claim-code counter is enough until abuse is seen, and this entry is where that decision gets revisited. The Vercel region stays `hnd1`, next to the Supabase project. Consequences: member HTML never reaches the DOM; invoices in old emails (sent before this date) need the new link, which admin can copy from `/admin/orders`; every test in `tests/unit.test.ts` that pins these behaviours must stay green.

## ADR-40 · Admin API keys made in admin, not in the environment
**Accepted · 2026-09-19**
Context: One `ADMIN_API_KEY` in the host's environment served the scheduled editorial task. The founder wants to hand external tools (other automations, scripts, integrations) the full admin API without a login or an MCP, and to cut any one of them off without touching the others. Decision: an `api_keys` table (name, shown prefix, SHA-256 of the key, role `editor` or `admin`, maker, last use, `revoked_at`) and an admin-only page `/admin/api-keys` that makes a key (`spk_` plus 64 hex characters from Web Crypto, shown once) and revokes it. `getSessionUser()` honours a bearer that matches the environment key (acts as the first admin) or the hash of an unrevoked row (acts as the maker with the key's role, and only while the maker still holds at least that role: a demoted or deleted admin takes their keys down with them); `last_used_at` is written at most every five minutes. The admin API returns 503 only when neither kind of key exists. Not adopted: scopes per route (a role is enough until a tool needs less than the desk), key expiry (revocation is one click), and making keys through the API itself (a leaked key must not be able to mint more). Consequences: the key check costs one indexed lookup per request; the environment key stays as a bootstrap and for the migration's contract suite; Web Crypto was chosen so the module runs unchanged on Workers.

## ADR-41 · Cloudflare Workers through vinext, OpenNext as the fallback
**Accepted · 2026-09-19** (migration Phase 1; docs/INVENTORY.md)
Context: The site moves from Vercel to Cloudflare Workers to run at near-zero cost with everything in one account. Cloudflare's own guidance recommends vinext, a Vite plugin that reimplements the Next.js API surface, with the OpenNext adapter as the other supported path. Decision: vinext. `npx vinext check` reported 91 percent compatibility with one issue (`"type": "module"`, added) and the first full build passed with every route classified; the built Worker boots under `wrangler dev` and serves route handlers, static routes and the social card. `next dev` and `next build` keep working unchanged, so Vercel stays the production host until Phase 9. Configuration: `vite.config.ts` (page cache through the Workers Cache, no KV data cache because the free plan allows 1,000 KV writes a day), `wrangler.jsonc` (`nodejs_compat`, static assets binding). Runtime-specific code lives in exactly one module pair, `src/lib/platform.ts` (Node) and `src/lib/platform.workerd.ts` (Workers), swapped by a `pre` Vite plugin because vinext resolves `@/` paths before `resolve.alias`; the same plugin stubs the local database engine out of the Workers bundle. Not adopted: rewriting `node:crypto` callers to Web Crypto (the compatibility layer provides them), the Rate Limiting binding (only 10 or 60 second windows; ours run to a day). Fallback: if vinext fails a later phase, OpenNext's custom worker pattern takes the same `platform.workerd.ts`. Consequences: two build pipelines until cutover; `.next/types/validator.ts` is excluded from the type check because vinext rewrites the generated route types; the 10 ms CPU limit of the Workers free plan is measured on a deployed staging Worker before Phase 2 starts.

## ADR-42 · Image scaling in WebAssembly: photon plus libwebp
**Accepted · 2026-09-19**
Context: Uploads and imported photos were normalised and given 480 and 960 px renditions by sharp, a native binary that cannot run on Workers. Decision: `@cf-wasm/photon` (Rust image library compiled to WebAssembly) decodes and resizes; `@jsquash/webp` (libwebp compiled to WebAssembly) encodes, because photon's own WebP encoder is lossless and produced files six times larger. Measured on a 1800 px photo: the 960 and 480 px renditions came out at 41 KB and 13 KB against sharp's 38 KB and 13 KB, so URLs, widths and page weight are unchanged. Both modules are handed in by `src/lib/platform.ts` (compiled from disk on Node, imported as WebAssembly modules on Workers, where compiling from bytes is refused). The R2 write goes through the `MEDIA` bucket binding on Workers and keeps the hand-signed S3 PUT elsewhere. Not adopted: EXIF auto-orientation (sharp did it; photon has no EXIF reader; revisit if sideways uploads appear), Cloudflare Images (paid). Consequences: decode plus resize costs 200 to 500 ms of CPU per image, which the Workers free plan (10 ms per request) cannot run; image work therefore needs the Workers Paid plan (USD 5 a month, 30 seconds of CPU) or must leave the request path.
